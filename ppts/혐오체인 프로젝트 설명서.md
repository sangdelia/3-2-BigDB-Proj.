# 혐오체인 프로젝트 설명서

> 한국어 유해표현 분석 웹 페이지 · BigDB 팀 프로젝트
> 팀: 조규상(모델·실험) · 서재철(데이터·자료) · 윤건호(웹·서비스)
> 기준: 중간발표 보완본(2026-11-05), 저장소 `sangdelia/blobfish` 브랜치

이 문서는 배경지식이 없는 사람을 위해 썼다. 개념은 등장 순서대로 하나씩 설명한다. 각 기법은 **왜 필요했는지 → 무엇을 확인했는지 → 어떤 결과가 나왔는지** 순서로 적었다.

## 1. 문제: 무엇을 왜 만드는가

### 1.1 유해표현

- **유해표현**: 특정 집단을 비하하거나, 사람을 공격하거나, 욕설을 담은 표현
- **혐오표현**: 유해표현 중 성별·연령·장애·직업·인종·종교·정치 같은 집단을 겨냥한 것

온라인 댓글은 양이 매우 많다. 사람이 모두 읽고 거르기 어렵다. 그래서 문장을 자동으로 판정하는 도구가 필요하다.

### 1.2 이 프로젝트가 정한 과제

처음에는 다른 방향을 제안했다.

- **초기 제안**: 비슷한 문장을 찾아 보여 주는 유사 사례 검색 시스템
- **방향 전환 이유**: 언어마다 구조가 다르고, 데이터 양과 라벨 체계도 다름
- **결정**: 한국어 데이터 6종에 집중하고, 검색 시스템은 후속 작업으로 미룸

최종 과제는 두 가지다.

| 구분 | 과제 | 입력 | 출력 |
|---|---|---|---|
| 모델 A | 분류 (주 과제) | 한국어 문장 1개 | 정상 / 유해 / 판단 보류 + 점수 0–100 |
| 모델 B | 점수 예측 (보조 과제) | 같은 문장 | Hate · 공격성 · 욕설 점수 각 0–100 |

입력 조건은 **1–1,000자, 한글 포함**이다.

## 2. 먼저 알아야 할 개념

### 2.1 머신러닝의 기본 용어

- **데이터**: 학습에 쓰는 문장 모음
- **라벨**: 사람이 문장마다 붙여 둔 정답 표시 (예: "혐오", "깨끗함")
- **정답 y**: 모델이 맞혀야 하는 값. 이 프로젝트에서는 정상 0 / 유해 1
- **속성 x (특징)**: 모델이 계산에 쓰는 숫자. 문장을 숫자로 바꾼 것
- **모델**: x를 받아 y를 추측하는 계산식
- **학습**: 정답을 잘 맞히도록 계산식의 숫자(가중치)를 조정하는 과정
- **지도학습**: 정답이 붙은 데이터로 학습하는 방식

이 프로젝트의 흐름은 네 단계다.

```
정답 만들기 → 숫자 속성 만들기 → 학습 → 평가
```

### 2.2 분류와 예측

- **분류**: 정해진 범주 중 하나를 고르는 과제 (정상 / 유해)
- **점수 예측**: 연속된 값을 내는 과제 (0–100점)

모델 A는 분류다. 모델 B는 내부적으로 0·1·2 등급을 분류한 뒤, 그 결과를 점수로 바꾼다.

### 2.3 데이터를 셋으로 나누는 이유

모델이 학습한 문장으로 성능을 재면 점수가 부풀려진다. 이미 본 문제를 다시 푸는 것과 같기 때문이다. 그래서 데이터를 셋으로 나눈다.

| 묶음 | 용도 | 비율 | 행 수 (모델 A) |
|---|---|---|---|
| train | 학습 | 80% | 249,732 |
| validation | 설정·기준값 선택 | 10% | 30,580 |
| test | 최종 성능 보고 | 10% | 31,349 |

- **원칙**: 선택은 validation으로만 함. test는 마지막에 한 번만 봄
- **이유**: test를 보고 설정을 고르면, test에 맞춘 결과가 되어 실제 성능을 과대평가함

## 3. 데이터

### 3.1 사용한 6종 데이터

| 출처 | 내용 | 정제 후 행 | 유해 비율 |
|---|---|---|---|
| K-HATERS | 뉴스 댓글, 혐오 강도 4단계 | 168,727 | 73.4% |
| K-MHaS | 혐오 유형 다중 표시 | 78,540 | 45.4% |
| KOLD | 뉴스 댓글 공격 여부 | 40,178 | 50.4% |
| UnSmile | 혐오 유형 9개 + 깨끗함 | 14,984 | 75.1% |
| BEEP | 연예 뉴스 댓글 3단계 | 7,123 | 54.0% |
| NIKL | 대화 속 발화의 적절성 | 2,109 | 67.2% |
| **합계** | | **311,661** | **63.0%** |

### 3.2 라벨을 하나의 정답으로 통일

**원인.** 출처마다 라벨 체계가 다르다. 어떤 곳은 "공격적"을, 어떤 곳은 "혐오 유형 번호"를 쓴다. 이대로는 한 모델로 학습할 수 없다.

**처리.** 모든 라벨을 정상 0 / 유해 1로 바꿨다. 같은 문장에 서로 모순된 라벨이 붙은 경우는 제외했다.

| 출처 | 정상 = 0 | 유해 = 1 | 제외 |
|---|---|---|---|
| NIKL | 적절 | 부적절 | — |
| UnSmile | 깨끗함만 표시 | 혐오 유형 1개 이상 | 깨끗함 + 혐오 동시 |
| KOLD | 공격 아님 | 공격적 | — |
| K-MHaS | "혐오 아님"(8)만 | 혐오 유형(0–7)만 | 8과 0–7 혼재 |
| K-HATERS | 정상 | 공격적 · 약한 혐오 · 강한 혐오 | 그 외 라벨, 빈 문장 |
| BEEP | 없음 | 공격적 · 혐오 | — |

**결과.** 정상 115,328행(37.0%), 유해 196,333행(63.0%).

**주의.** 출처마다 "유해"의 기준이 다르다. 이 차이가 뒤에서 오류의 원인으로 다시 나온다(11장).

### 3.3 EDA: 데이터 현황 파악

- **EDA (탐색적 데이터 분석)**: 모델을 만들기 전에 데이터의 크기·분포·빈 값을 먼저 살펴보는 작업

확인한 내용은 다음과 같다.

| 항목 | 결과 |
|---|---|
| 필수값(문장·라벨·출처) 결측 | 0건 |
| 문장 길이 중앙값 | 35자 |
| 가장 큰 출처 | K-HATERS 54.1% |
| 유해 비율 | 63.0% |
| 선택 주석 미제공률 | 문맥 84.1% · 대상 43.6% · 표현 42.6% |

**발견 1: 불균형.** 출처도, 라벨도 한쪽으로 치우쳐 있다.

- **불균형 데이터**: 한 클래스가 다른 클래스보다 훨씬 많은 데이터
- **문제점**: 모델이 많은 쪽(유해)으로 쏠려 판정하기 쉬움
- **대응**: 평가는 Macro-F1로(9장), 학습은 클래스 가중치로(7장)

**발견 2: 선택 주석의 빈칸.**

- **선택 주석**: 문장·라벨 외에 출처마다 다르게 붙은 정보 (문맥, 공격 대상, 표현 위치)
- **분석**: 모두 필수로 하면 7,149행(2.3%)만 남고 304,512행을 버려야 함
- **결정**: 빈칸을 오류로 보지 않고 삭제하지 않음. 이진 학습에는 쓰지 않음

## 4. 전처리: 학습용 데이터 만들기

- **전처리**: 원천 데이터를 학습에 쓸 수 있는 형태로 정리하는 과정

| 단계 | 하는 일 | 결과 행 수 | 도구 |
|---|---|---|---|
| 1 수집·파싱 | 6종을 같은 형식(공통 스키마)으로 변환 | 316,574 | Python |
| 2 필수값 검사 | 빈 문장·라벨 누락 제외 | 316,571 (−3) | Python |
| 3 정제 | 공백 정규화 · 충돌 제외 · 중복 병합 | 311,661 (−4,910) | Python + **Spark** |
| 4 그룹 분할 | 연결 그룹 단위 80/10/10 | 249,732 / 30,580 / 31,349 | Python |
| 5 저장·집계 | HDFS 저장 + MapReduce 집계 | 27개 키 일치 | **Hadoop** |
| 6 학습 | 문자 TF-IDF + 로지스틱 회귀 | 모델 2종 | scikit-learn |

### 4.1 공백 정규화 · 충돌 제외 · 중복 병합 (3단계)

**원인.** 같은 문장이 띄어쓰기만 다르게 여러 번 들어 있다. 같은 문장에 서로 다른 정답이 붙은 경우도 있다.

**처리.**
- **공백 정규화**: 연속 공백·줄바꿈을 하나로 맞춰 같은 문장으로 인식. 저장된 원문은 그대로 둠
- **충돌 제외**: 같은 문장에 정상·유해가 모두 붙으면 제외
- **중복 병합**: 같은 문장·같은 정답은 하나로 합침

**결과.** 316,571행 → 311,661행.

### 4.2 연결 그룹 분할 (4단계)

**원인.** 비슷한 문장이 train과 test에 나뉘어 들어가면, 모델이 사실상 정답을 미리 본 셈이 된다. 이것을 **데이터 누수**라고 한다.

**처리.** 서로 연결된 문장을 한 그룹으로 묶고, 그룹째 train·validation·test 중 한 곳에 넣었다.

**결과.** 누수로 인한 점수 부풀림을 줄인 80/10/10 분할.

## 5. 빅데이터 처리: HDFS · Spark · MapReduce

### 5.1 도구 개념

- **분산 처리**: 큰 작업을 여러 조각으로 나눠 동시에 처리하는 방식
- **Hadoop**: 분산 저장과 분산 계산을 위한 오픈소스 도구 모음
- **HDFS**: Hadoop의 분산 파일 시스템. 큰 파일을 블록으로 나눠 저장
- **MapReduce**: Map에서 (키, 값)을 내고, Reduce에서 같은 키끼리 합치는 집계 방식
- **Combiner**: Reduce 전에 미리 합쳐 전송량을 줄이는 단계
- **Spark**: 메모리 기반 분산 처리 엔진. SQL로 데이터 변환 가능
- **Parquet**: 열 단위로 저장하는 압축 파일 형식
- **해시 (SHA-256)**: 데이터를 고정 길이 값으로 요약한 지문. 한 글자만 달라도 값이 바뀜

### 5.2 왜 결과를 Python과 비교했나

**원인.** 새 도구로 처리한 결과가 맞는지 따로 확인할 방법이 필요하다.

**방법.** 같은 작업을 Python으로도 처리했다. 그리고 두 결과의 해시와 집계 값을 비교했다.

**의미.** 값이 같으면 빅데이터 도구가 데이터를 바꾸거나 잃지 않았다는 근거가 된다.

### 5.3 실험 1: 같은 정제 구간을 Python과 Spark로 비교

단일 서버에서 3단계 정제를 두 방식으로 실행했다. 각 3회 실행한 중앙값이다.

| 규모 | Python | Spark local[4] |
|---|---|---|
| 10,000행 | 0.110초 | 0.808초 |
| 100,000행 | 1.332초 | 2.110초 |
| 316,571행 | 4.706초 | **3.778초** |

- **결과 일치**: 세 규모 모두 출력 키 해시 일치 (3/3)
- **속도**: 31.7만 행에서만 Spark가 더 짧음
- **주의**: Spark 시작 시간 3.302초는 별도. 시작 비용까지 넣으면 빠르다고 말할 수 없음
- **local[4]**: 클러스터 없이 한 컴퓨터에서 4개 작업 스레드로 실행하는 모드

**해석.** 작은 데이터에서는 Spark의 준비 비용이 더 크다. 데이터가 커질수록 그 비용이 상대적으로 작아진다.

### 5.4 실험 2: Hadoop으로 저장·집계 검증

| 단계 | 내용 | 결과 |
|---|---|---|
| 입력 준비 | 출처·라벨·길이만 추출 (원문 제외) | 311,661행 |
| HDFS 적재 | 정제 데이터와 집계 입력 저장 (복제 수 1) | 저장 완료 |
| MapReduce | Mapper → Combiner → Reducer | 1,558,305건 → 27개 키 |
| 검증 | Python 독립 집계, 다시 읽은 Parquet 해시 | 27/27 일치, 해시 일치 |

- **원문을 뺀 이유**: 집계에는 출처·라벨·길이만 필요
- **27개 키**: 출처별 6 · 라벨별 2 · 출처×라벨 12 · 길이 구간 6 · 전체 1

### 5.5 실험 3: HDFS–Spark 연동 파이프라인

**원인 (피드백).** 중간발표에서는 Spark와 Hadoop을 따로 실행했다. "두 도구가 데이터를 정리하는 하나의 흐름이어야 한다"는 피드백을 받았다.

**처리.** 데이터를 세 층으로 나눠 모두 HDFS에 두고, 도구들이 HDFS에서 읽고 쓰게 연결했다.

- **Bronze**: 원천 그대로 저장한 층
- **Silver**: 정제한 층
- **Gold**: 집계 결과 층

```
로컬 원천 316,571행
  └─[HDFS 적재]→ Bronze (64.4MB Parquet)
        └─[Spark: HDFS에서 읽어 정제]→ Silver 311,661행
              ├─[Spark SQL 집계]→ Gold (27개 키)
              └─[MapReduce 집계]→ Gold (27개 키)
  └─[검증] Python = Spark = MapReduce
```

**결과 (2026-11-05 실행).** 검사 6개가 모두 일치했다.

| 검사 | 결과 |
|---|---|
| HDFS에서 다시 읽은 해시 = 로컬 해시 | 일치 |
| Bronze 행 수 | 일치 |
| Spark 출력 키 해시 = Python | 일치 |
| Spark 집계 = Python | 27/27 |
| MapReduce 집계 = Python | 27/27 |
| MapReduce 집계 = Spark | 27/27 |

- **소요 시간**: Spark 20.7초 (시작 3.5초 별도) · MapReduce 7초

### 5.6 빅데이터 처리의 한계

- 모두 **단일 서버**에서 실행함. 여러 서버로 늘렸을 때의 효과는 측정하지 않음
- 연결 그룹 분할과 모델 학습은 Python이 맡음
- 따라서 "분산 처리로 빨라졌다"는 결론은 내릴 수 없음
- 확인한 것은 **같은 결과를 빅데이터 도구로 재현할 수 있다**는 점

## 6. 문장을 숫자로 바꾸기: 문자 n-gram TF-IDF

모델은 글자를 직접 계산하지 못한다. 그래서 문장을 숫자 벡터로 바꿔야 한다.

### 6.1 문자 n-gram

- **n-gram**: 연속된 n글자 조각
- **2–5gram**: 2글자부터 5글자까지의 조각을 모두 사용
- **띄어쓰기**: 조각에 포함 (아래 표의 `␣`)

예: "멍청한" → 2글자 조각 "멍청", "청한" / 3글자 조각 "멍청한"

**이 방식을 쓴 이유.**
- 띄어쓰기 차이에 덜 민감함 (단어가 붙어 있어도 조각은 같음)
- 형태소 분석기 없이 바로 적용 가능

**대가.** 단어의 뜻과 문맥을 모른다. 이 약점이 11장의 오류로 이어진다.

### 6.2 TF-IDF

조각마다 숫자를 매기는 규칙이다.

- **TF (조각 빈도)**: 이 문장에 그 조각이 몇 번 나왔는지
- **DF (문서 빈도)**: 전체 문장 중 그 조각이 나온 문장 수
- **IDF (역문서 빈도)**: 흔한 조각일수록 작아지는 값

계산은 세 단계다.

1. **조각 빈도**: tf(t, d) = 문장 d에서 조각 t가 나온 횟수
2. **TF-IDF**: x_t = (1 + ln tf) × idf(t), idf(t) = ln((1 + N) / (1 + df(t))) + 1
3. **길이 정규화**: x ← x / ‖x‖₂ (긴 문장이 큰 값을 갖지 않게 함)

여기서 N은 train 문장 수 249,732다.

**의미.** 이 문장에 자주 나오고, 전체에서는 드문 조각일수록 큰 값을 받는다.

### 6.3 조각 사전

- **사전 크기**: 모델 A 200,000개, 모델 B 100,000개 조각
- **계산 범위**: 사전과 IDF는 train에서만 계산 (누수 방지)
- **결과**: 문장 하나 = 20만 차원 숫자 벡터. 대부분은 0

### 6.4 예시: "너는 정말 멍청한 바보야."

- 2–5글자 조각 46개가 나온다
- 그중 사전에 있는 28개만 0이 아닌 값을 가진다

| 조각 | x (TF-IDF) | w (모델 A 가중치) | x · w |
|---|---|---|---|
| 멍청 | 0.190 | 4.273 | 0.812 |
| ␣멍 | 0.187 | 2.698 | 0.505 |
| 바보 | 0.195 | 2.510 | 0.489 |
| 멍청한 | 0.208 | 1.832 | 0.381 |
| 청한 | 0.206 | 1.764 | 0.362 |
| … 나머지 23개 | | | … |
| **합계** | | | **5.733** |

이 합계가 다음 장 수식의 출발점이다.

### 6.5 쓰지 않은 정보

- 출처, 그룹 ID, 원래 세부 라벨은 속성으로 쓰지 않았다
- **이유**: 실제 서비스 입력에는 문장만 있기 때문

## 7. 모델 A: 정상 / 유해 분류

### 7.1 로지스틱 회귀

- **로지스틱 회귀**: 속성마다 가중치를 곱해 더한 뒤, 0–1 사이 확률로 바꾸는 선형 분류기
- **장점**: 어떤 조각이 점수를 올렸는지 직접 볼 수 있음

계산은 세 단계다.

**① 확률 계산**

```
z = wᵀx + b
P(유해 | x) = σ(z) = 1 / (1 + e^(−z))
```

- **w**: 조각별 가중치 20만 개
- **b**: 절편 (기본값)
- **σ (시그모이드)**: 어떤 실수든 0–1 사이 값으로 바꾸는 함수

**② 학습 (손실 최소화)**

```
min  ½‖w‖² + C · Σᵢ c_yᵢ · log(1 + e^(−ỹᵢ zᵢ))
```

- **손실**: 틀린 정도를 숫자로 나타낸 값. 학습은 이 값을 줄이는 과정
- **½‖w‖² (L2 규제)**: 가중치가 지나치게 커지는 것을 막아 과적합 방지
- **과적합**: train에만 맞춰져 새 문장에서 성능이 떨어지는 현상
- **C = 1**: 규제 강도
- **ỹ**: 정답을 ±1로 표시한 값

**③ 판정**

| 조건 | 판정 |
|---|---|
| P ≥ 0.43 | 유해 |
| P < 0.43 | 정상 |
| 사전에 있는 조각이 0개 | 판단 보류 (점수 숨김) |

점수는 100 × P로 보여 준다. 즉 43점 이상이면 유해다.

### 7.2 클래스 가중치: 불균형 대응

**원인.** 유해가 63%라서, 모델이 유해 쪽으로 쏠리기 쉽다.

**처리.** 적은 클래스의 오류에 더 큰 벌점을 준다.

```
c_y = N / (2 · N_y)
```

N은 전체 문장 수, N_y는 그 클래스의 문장 수다. 정상 문장이 적으므로 정상 문장을 틀렸을 때 손실이 더 커진다.

### 7.3 판정 기준 0.43과 설정 선택

- **판정 기준**: validation에서 Macro-F1이 가장 높은 값 (0.05–0.95 범위 탐색)
- **설정**: 조각 길이(3–5 / 2–5) × 사전 크기(6만 / 20만) 4가지를 validation에서 비교 → 2–5gram · 20만 선택

### 7.4 예시 계산

"너는 정말 멍청한 바보야."

```
z = 5.733 + (−1.341) = 4.392
P = σ(4.392) = 0.988 → 98.8점 ≥ 43 → 유해
```

## 8. 모델 B: Hate · 공격성 · 욕설 점수

### 8.1 왜 별도 모델인가

**원인.** 모델 A는 "유해한가"만 답한다. 어떤 종류의 유해인지는 알려 주지 않는다.

**처리.** K-HATERS 원본에는 항목별 평점이 있다. 이것으로 세 가지 점수를 따로 학습했다.

- **평점 (Ratings)**: 문장마다 13개 항목에 0·1·2로 매긴 강도 표시
- **데이터**: K-HATERS 공식 분할 train 172,097 · validation 9,997 · test 9,997

모델 B는 7번째 데이터가 아니라 **별도 데이터 · 별도 모델**이다.

### 8.2 정답 만들기

| 점수 | 정답 등급 (0·1·2) |
|---|---|
| Hate | 집단 평점 7개(성별·연령·장애·직업·인종·종교·정치) 중 최댓값 |
| 공격성 | 평점 13개 전체 중 최댓값 |
| 욕설 | 욕설 평점 |

### 8.3 계산

**① 확률 (다항 로지스틱 회귀)**

```
z_k = w_kᵀx + b_k,  k ∈ {0, 1, 2}
P(k | x) = e^(z_k / T) / Σⱼ e^(z_j / T)
```

- **다항 로지스틱 회귀**: 셋 이상의 등급을 고르는 로지스틱 회귀
- **softmax**: 등급별 값을 합이 1인 확률로 바꾸는 함수
- **온도 T**: 확률이 지나치게 확신하지 않도록 조정하는 값. validation에서 1.0 선택

**② 점수**

```
S = 50 × (P(1) + 2 · P(2))
```

- 모두 0등급이면 0점, 모두 2등급이면 100점
- **의미**: 예측 등급의 평균을 0–100으로 바꾼 값
- **주의**: 정답 확률도, 피해 심각도도 아님

### 8.4 판정 기준

모델 B에는 판정 기준이 없다. 세 점수를 함께 보여 주기만 한다.

### 9.1 혼동행렬

## 11. 오류 분석: 어디서 왜 틀리는가

### 11.1 출처별 오류

**분석.** test를 출처별로 나눠 봤다.

| 출처 | 문제 | 값 |
|---|---|---|
| BEEP | 유해를 많이 놓침 (재현율 낮음) | 유해 재현율 40.97% |
| K-HATERS | 정상을 많이 유해로 판정 | 정상 오탐률 38.78% |

validation 재진단에서도 같은 방향이 나왔다.

- BEEP 실제 유해의 50.77%를 놓침
- K-HATERS 실제 정상의 39.37%를 오탐
- 201자 이상 실제 정상의 56.65%를 오탐

**원인 추정.** 출처마다 "유해"의 기준이 다르다. 한 출처에서 정상인 표현이 다른 출처에서는 유해로 표시되어 있을 수 있다. 원인 확인은 후속 실험 E4로 남겼다.

**주의.** 라벨 정의가 달라서 출처끼리 성능 우열을 비교하는 것은 아니다.

### 11.2 부정문 오류

- **입력**: "너는 바보가 아니야."
- **결과**: 43.80점 ≥ 43 → 유해 (오탐)
- **원인**: 문자 조각 "바보"는 유해 쪽 가중치를 가짐. 모델은 "아니야"가 뜻을 뒤집는다는 것을 모름
- **근본 원인**: 문자 조각 방식은 문맥을 보지 않음 (6.1)

### 11.3 동음이의어 오류: "시래기"

- **입력**: "시래기" (말린 채소)
- **결과**: 74.33점 → 유해 (오탐)
- **원인**: 학습 데이터에서 "시래기"가 나온 9건이 모두 "쓰레기"의 변형 욕설이었음
- **구조**: 입력이 짧아 조각 하나("래기")가 점수를 결정함

### 11.4 개선 실험: 판단 보류 규칙

**원인.** 오탐의 상당수가 두 유형에 몰려 있었다.
- 기준 43 바로 위의 애매한 점수
- 조각 한두 개가 점수를 좌우하는 짧은 입력

**처리.** 모델은 다시 학습하지 않았다. 대신 이 두 경우를 "판단 보류"로 돌리는 규칙을 만들었다.

- **R1 경계 보류**: 43 ≤ 점수 < 48 → 보류
- **R2 단일 조각 보류**: 인식 조각 ≤ 2개 · 최대 조각 비중 ≥ 60% · 점수 < 80 → 보류
- **선택 방법**: validation에서 보류율 5% 이하 중 자동 판정 Macro-F1이 가장 높은 규칙

**결과 (test).**

| 입력 | 점수 | 규칙 적용 후 |

**한계.**
- 보류된 1,501건 중 844건은 실제 유해 → 사람 검토가 필요
- 처음 정한 선택 기준(재현율 유지)으로는 어떤 규칙도 뽑히지 않았음. 기준을 한 번 바꾼 뒤 test를 평가했으므로 독립 검증으로 보지 않음
- 부정문·동음이의어 자체를 고친 것은 아님. 근본 해결은 문맥 모델(E3)의 몫
- 웹 서비스에는 아직 반영하지 않음

| 모델 B 제한 정규화 (v2) | 변형 표기 8종 정리 | Hate MAE 19.9905 → 19.8762 | **채택** |
| 모델 A 문자 2–8gram | 더 긴 조각 사용 | Macro-F1 하락 | 기존 유지 |
| 선택 주석 필수화 | 정보가 완전한 행만 사용 | 2.3%(7,149행)만 남음 | 미채택 |

형태소 비교는 소규모 표본 · 단일 시드 결과다. 운영 모델과 직접 비교하지 않는다.

## 13. 웹 시연

- **구성**: 저장한 모델을 Flask 웹 API로 호출, 결과와 근거 특징을 화면에 표시
- **동작**: 한 입력을 모델 A·B에 동시에 보냄
- **화면 상단**: 모델 B의 Hate · 공격성 · 욕설 점수
- **화면 하단**: 모델 A 판정, 점수를 올린 조각, 후보 구간 삭제 전후 점수 변화
- **공개 방식**: Cloudflare 터널 + systemd 서비스 (부팅 시 자동 시작, 종료 시 자동 재시작)

실제 화면 예시는 다음과 같다.

| 입력 | 결과 |
|---|---|
| 일반 문장 | 0.57점 → 정상 |
| 부정문 | 43.80점 → 유해 (오탐) |
| 욕설 문장 | 95.57점 → 유해, 욕설 점수 58.43 |
| 학습한 조각이 없는 입력 | 판단 보류 |

대체 자료로 46초 시연 영상도 있다.

## 14. 한계와 후속 계획

### 14.1 현재 한계

- **내부 평가**: test는 같은 6종 안에서 나눈 것. 독립 외부 평가가 아님
- **문맥 미반영**: 부정·인용·동음이의어를 구분하지 못함
- **짧은 입력**: 조각 하나가 판정을 좌우함
- **출처별 기준 차이**: 특히 K-HATERS 오탐률이 높음
- **모델 B 점수**: 확률이나 심각도가 아님. 약한 혐오(1등급)를 0등급으로 놓치는 경우가 많음
- **빅데이터 처리**: 단일 서버. 확장성은 측정하지 않음

### 14.2 후속 실험

현재 모델(문자 TF-IDF + 로지스틱 회귀)을 기준선으로 고정하고 비교한다.

| 실험 | 목적 | 지표 |
|---|---|---|
| E1 오류 유형 평가셋 | 부정·인용·동음이의어 오탐 측정 | 유형별 오탐률 |
| E2 짧은 입력 보류 | 조각 1–2개로 판정하는 문제 완화 (1차 결과: 11.4) | 정상 오탐률 · 보류율 |
| E3 문맥 모델 | 사전학습 언어 모델이 문맥을 반영하는지 확인 | Macro-F1 · 유형별 오탐 |
| E4 출처×길이 분석 | 출처별 라벨 정의 차이 확인 | 재현율 · 오탐률 |

- **사전학습 언어 모델**: 대량의 문장으로 미리 학습해 단어 순서와 문맥을 반영하는 모델
